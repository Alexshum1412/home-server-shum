# ADR-0004. Резервное копирование

- **Статус:** принято · 16.10.2026 · реализация — Implemented / Partial (нет копии вне дома и шифрования)

## Контекст

- Один рабочий диск `C:`; второй внутренний диск неисправен (`ST_M13FQBL`, не трогать).
- Есть USB-флешка ADATA, отформатированная в NTFS с меткой тома `reserve` (сейчас `D:`, буква может меняться).
- Данные портала небольшие (на 16.10.2026 копия весит 8,1 МБ вместе с кодом), но содержат хэши паролей и журнал.
- Дашборд с самого начала показывает статус копирования только из `backup-status.json` и не считает копию существующей без проверки (спецификация `system-status`).
- Сторонних инструментов копирования на ПК нет; решение должно работать без прав администратора и без новых загрузок — на том, что уже установлено: Node.js 24 и Git.

## Решение

1. **Свой небольшой механизм на Node.js** (`server/src/backup/`, CLI `server/src/cli/backup.ts`, обёртка `scripts\backup.cmd`) без новых зависимостей.
2. **Места хранения** (`BACKUP_TARGETS`, по умолчанию): `C:\FamilyServer\backups` и `label:reserve\FamilyServerBackups` — папка на томе с меткой `reserve`, где бы Windows его ни подключила (поиск через фиксированный read-only скрипт `Get-Volume`). Каждое место пишется и проверяется независимо; ошибка одного не мешает другому, но весь запуск считается неуспешным.
3. **Формат:** папка `family-backup-YYYYMMDD-HHMMSS` (UTC): `data\` (данные портала без `sessions.json`, логов, `run\`, `*.tmp`), `config\.env`, `repo.bundle` (`git bundle create --all` — вся история кода), `network\tailscale-serve.json`, `system-info.json`, `manifest.json` с SHA-256 каждого файла. Данные — обычные JSON-файлы, читаются без специальных программ; код — стандартный `git clone`.
4. **Целостность:** запись в `<имя>.partial` → повторное чтение и сверка SHA-256 + `git bundle verify` → переименование в окончательное имя. Восстановление тоже сверяет каждый файл; `test-restore` восстанавливает свежие копии во временную папку и сравнивает HEAD кода с манифестом — только после полного успеха пишется `restoreTestedAt`.
5. **Восстановление никогда не пишет в рабочую папку данных** — только в новую пустую папку; замена данных — вручную при остановленном сервере.
6. **Хранение:** 14 копий в каждом месте (`BACKUP_KEEP`); старые удаляются только после записи и проверки новой; ссылки (junction/symlink) не обходятся; корень диска и папка данных как место хранения запрещены.
7. **Расписание:** задача планировщика текущего пользователя «FamilyServerBackup», ежедневно в 03:30, `StartWhenAvailable`, только при выполненном входе (пароль в планировщике не хранится).
8. **Статус:** `backup-status.json` (`lastRunAt`, `lastResult`, `lastSuccessAt`, `restoreTestedAt`, `targets`, `warnings`) → дашборд: «Последняя копия …: основной диск — да, флешка «reserve» — да»; ошибка любого места → состояние «ошибка» и предупреждение.
9. **Шифрования пока нет.** Обе копии остаются дома, на носителях владельца; пароли — хэши scrypt. Потерянная флешка → смена паролей.
10. **GitHub — только код, третье место копий.** Публичный репозиторий `https://github.com/Alexshum1412/home-server-shum` (опубликован 17.10.2026 с согласия владельца; e-mail в коммитах заменён на служебный `…@users.noreply.github.com`). Каждый запуск копирования (`BACKUP_GIT_PUSH=origin/main`) отправляет закоммиченный код: только fast-forward (никогда `--force`), без окон входа (`GCM_INTERACTIVE=never`), только на `https://github.com/…`. Сбой отправки (нет интернета, истёк вход, на GitHub чужие коммиты) — **замечание**, а не провал копирования: семейные данные защищают локальные копии. Данные семьи, `.env`, логи и копии в GitHub не отправляются никогда.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| `robocopy /MIR` по расписанию | нет проверки содержимого по хэшам и версий: испорченный или удалённый файл тихо «зеркалится» в копию; нет статуса для дашборда |
| «История файлов» Windows | рассчитана на папки профиля и библиотеки, настраивается через GUI; нет автоматической проверки восстановления и статуса для дашборда; без собственного шифрования |
| restic / Kopia | версии и шифрование «из коробки» — хороший кандидат для будущей копии вне дома, но на ПК **не установлены**; установка — отдельное решение владельца после проверки официальной документации |
| Копировать данные в Git/GitHub | недопустимо: персональные данные и хэши паролей в публичном репозитории |

## Последствия

- Проверено 16.10.2026: копия в оба места (по 8,1 МБ), `verify`, `test-restore` (HEAD `0538b45418fa` совпал), ручное восстановление с флешки (SHA-256 `services.json` и `audit.jsonl` совпали с рабочими), запуск задачи из планировщика (`LastTaskResult 0`).
- Копия на `C:` не спасает от отказа диска; флешка не спасает от кражи или пожара. Вынутая флешка видна на дашборде как ошибка.
- В `repo.bundle` попадает только закоммиченный код.
- Будущие семейные данные (фото, медиа) в копию пока не входят — расширить при установке сервисов.
- Осталось: зашифрованная копия вне дома; исправный второй диск. Ранбук — `docs/runbooks/backup-restore.md`.
